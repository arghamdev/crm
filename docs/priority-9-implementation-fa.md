# اولویت ۹ — گزارش‌ها و تحلیل

## مبنای دامنه و نتیجه تحلیل

در برنامه پیشین، اولویت ۹ شامل KPI Catalog، داشبوردهای مدیرعامل/فروش/منطقه/شعبه، Forecast، Target Achievement، Collection، Dealer Performance، Conversion Funnel، Data Quality، Export امن و مرز BI/Data Warehouse است. Portal و Mobile متعلق به اولویت ۱۰ باقی می‌مانند.

| شکاف نسخه اولویت ۸ | تصمیم اجرایی اولویت ۹ |
|---|---|
| گزارش‌های پراکنده و فرمول نامشخص | سرویس واحد `ReportingService` و فرهنگ ۹ شاخص |
| احتمال تفاوت دامنه KPI، ریزداده و Export | یک مسیر ساخت Fact با اشتراک مجوز گزارش و مجوز منبع |
| اشتباه گرفتن سفارش پرداخت‌شده با وجه وصولی | Port مستقل `IReportingFinanceSource` در سطح فاکتور |
| تکرار Snapshot پس از Sync | انتخاب آخرین نسخه در grain مشخص؛ عدم جمع نسخه‌ها |
| نسبت هدف با دوره متفاوت | آخرین دوره مشترک؛ تطبیق دقیق ابتدا و انتهای هدف/عملکرد |
| نشت مبلغ از خروجی مستقیم | مجوز مستقل `Reporting.Financial.Read` در لایه Application |
| CSV Formula Injection | Quote همه سلول‌ها و خنثی‌سازی فرمول و Control character |
| خروجی بدون قابلیت پیگیری | ثبت Actor، شرکت، فیلتر، تعداد، فرمت، Correlation و Schema در Audit |
| ادعای تاریخی از داده عملیاتی فعلی | برچسب «تصویر فعلی»؛ عدم ارائه Accuracy تاریخی ساختگی |

## معماری و مالک داده

`ReportsController → IReportingService → ICrmDataStore + IReportingFinanceSource`

مدل‌های خروجی شامل `ReportingDashboard`، `ReportKpi`، `ReportFact`، `ReportBreakdown`، `ReportFunnelStage` و `ReportDrilldown` هستند. Entity مستقیماً به Razor یا JSON داده نمی‌شود. گزارش‌ها رکورد عملیاتی را تغییر نمی‌دهند؛ Export فقط رسید ممیزی را در `SecurityAuditEvents` موجود ثبت می‌کند. این مرحله به Migration جدید نیاز ندارد.

منابع:

- Pipeline/Forecast/Won: فرصت‌های CRM؛ مبلغ نمونه IRR
- Conversion: cohort سرنخ‌های ایجادشده در بازه، با وضعیت فعلی
- Quality: کامل‌بودن پنج فیلد مشتری، مستقل از فیلتر تاریخ
- Collection/Overdue: Snapshot فاکتور حسابداری نمونه، با `InvoiceId` یکتا
- Dealer Actual: آخرین Snapshot معتبر ERP/BI در دوره مشترک
- Dealer Target: هدف CRM با ابتدا/انتهای دقیقاً برابر با Actual

## تعریف شاخص‌ها

| کلید | محاسبه | نکته |
|---|---|---|
| `pipeline` | جمع ارزش فرصت باز با ExpectedClose داخل بازه | شامل Won/Lost نیست |
| `forecast` | جمع ارزش × احتمال مرحله / ۱۰۰ | معادل فروش قطعی نیست |
| `won` | جمع ارزش Won با ClosedAt داخل بازه | معادل مبلغ فاکتور نیست |
| `conversion` | تعداد Converted / همه سرنخ‌های cohort × ۱۰۰ | مخرج صفر = ناموجود |
| `quality` | فیلدهای تکمیل‌شده / (تعداد مشتری × ۵) × ۱۰۰ | نام، شهر، شناسه ملی، تلفن، ایمیل؛ سنجه صحت نیست |
| `collection` | وصول تجمعی / مبلغ فاکتورهای cohort × ۱۰۰ | وصول تا Snapshot، نه جریان وجه در تاریخ پرداخت |
| `overdue` | مبلغ فاکتور − وصول برای سررسید گذشته | روی همان cohort فاکتور |
| `dealerAchievement` | جمع Actual / جمع Target هم‌دوره × ۱۰۰ | هدف ناموجود در مخرج صفر پنهان نمی‌شود |
| `dealerSales` | جمع آخرین Actual هر نماینده در دوره مشترک | با فروش مستقیم جمع نمی‌شود |

نرخ کل و نرخ هر شعبه از جمع صورت و مخرج محاسبه می‌شود، نه از میانگین درصدها. ریزداده صورت و مخرج را نمایش می‌دهد تا تطبیق ممکن باشد. نبود داده با «—» از مقدار صفر واقعی جداست.

قیف، تعداد سرنخ‌های دوره، تماس ثبت‌شده، وضعیت فعلی Qualified/Converted و Converted را نشان می‌دهد. این نمایش رویدادهای تاریخی تمام مراحل را بازسازی نمی‌کند.

## زمان، واحد و تازگی

- تاریخ ورودی گزارش در نسخه نمونه، میلادی و مرز روز UTC است و در فرم صریحاً نوشته شده است.
- ابتدا شامل و پایان داخلی غیرشامل است: `[From 00:00 UTC, To+1 00:00 UTC)`.
- حداکثر بازه ۳۶۶ روز؛ بازه معکوس و تاریخ نامعتبر رد می‌شود.
- Snapshot آینده وارد گزارش نمی‌شود؛ تکرار فاکتور با آخرین زمان Sync حذف می‌شود.
- Snapshot قدیمی‌تر از ۱۵ دقیقه با شمارش Stale مشخص است.
- داده مالی با ارز غیر IRR، مبلغ نامعتبر یا شعبه/قلمرو ناسازگار حذف و هشدار داده می‌شود.
- هدف یا عملکرد مفقود نماینده شمارش می‌شود. بازه بزرگ باعث جمع دوره‌های غیرقابل‌مقایسه نمی‌شود.

## مجوزها و جلوگیری از نشت

| Permission | مسئولیت |
|---|---|
| `Reporting.Read` | صفحه و ریزداده در Scope گزارش |
| `Reporting.Export` | CSV؛ دوباره ارزیابی Scope این مجوز |
| `Reporting.BiExport` | بسته JSON نسخه ۱؛ دوباره ارزیابی Scope |
| `Reporting.Financial.Read` | صورت/مخرج وصول و سررسید مالی |

هر Fact باید هم مجوز گزارش و هم مجوز ماژول مبدأ را در همان شرکت و رکورد داشته باشد. Scope نشست Company/Branch/Territory نیز اعمال می‌شود. Region از زیرمجموعه‌های ساختار سازمانی محاسبه شده و فقط فیلتر محدودکننده است. گزینه‌های فیلتر از ابعاد دادهٔ مجاز ساخته می‌شوند. تغییر Profile به مدیرعامل هیچ مجوزی ایجاد نمی‌کند. `dealer.user` به گزارش جامع داخلی دسترسی ندارد؛ نمای مستقل نماینده در ماژول قبلی باقی است.

کاربر جدید `reporting.ceo / Demo@1405` نقش Executive فقط‌خواندنی در C01 دارد. کاربر موجود SalesExpert گزارش بدون Export، SalesSupervisor گزارش شعبه و Export، FinanceManager گزارش مالی و ChannelManager گزارش شبکه دارد.

## قرارداد صفحات و Endpointها

| Endpoint | روش | خروجی و رفتار |
|---|---|---|
| `/reports` | GET | View کامل یا `_Dashboard` برای HTMX؛ فیلتر و History |
| `/reports/drilldown` | GET | View کامل یا `_Drilldown`؛ صفحه‌بندی ۱ تا ۱۰۰ ردیف |
| `/reports/export` | POST | CSV UTF-8 BOM با Anti-forgery و Audit |
| `/reports/bi/v1` | POST | JSON نسخه‌بندی‌شده با Anti-forgery و Audit |

فیلتر بدون JS نیز GET عادی انجام می‌دهد. خطای Binding یا قاعده بازه، پاسخ 422 است؛ HTMX خطا را در `#reportErrors` قرار می‌دهد و فرم را حفظ می‌کند. خروجی فایل با POST معمول مرورگر دانلود می‌شود. همه پاسخ‌های گزارش `no-store` هستند. سقف خروجی ۵۰۰۰ Fact است؛ بیشتر از سقف رد می‌شود و بی‌صدا بریده نمی‌شود.

## مرز BI و انبار داده

JSON با `schemaVersion=crm.reporting.v1` شامل زمان محاسبه، شرکت، فیلترها، تعریف KPI، صورت/مخرج، ابعاد شعبه/قلمرو و Factهای مجاز است. grain هر Fact برابر `Metric + RecordId` در همان بسته است؛ InvoiceId برای وصول و DealerId برای آخرین دوره مشترک نماینده استفاده می‌شود. مصرف‌کننده باید Metric را همراه RecordId کلید کند.

این بسته، قرارداد تحویل نمونه به BI است. ETL زمان‌بندی‌شده، Warehouse واقعی، تغییرات تدریجی، تاریخچه SCD، Snapshot ثابت تاریخی، Forecast Freeze/Accuracy و مدل چندارزی نیازمند داده و مقصد واقعی‌اند و اجراشده محسوب نمی‌شوند. هیچ Credential یا اتصال بیرونی ساخته نشده است.

## محدودیت نسخه نمونه

Store فعلی EF برای گزارش، DataSet نمونه را در حافظه Materialize می‌کند. قبل از حجم Production، Port خواندنی با Query/Projection سمت SQL، ایندکس و تست حجم لازم است. سقف تاریخ و Export جایگزین این بهینه‌سازی نیست. Accountهای نمونه فقط در Seed دیتابیس آزمایشی جدید ساخته می‌شوند؛ دیتابیس موجود بدون اجازه بازنشانی نمی‌شود.
