# گزارش تحلیل و بررسی پروژه Enterprise CRM

تاریخ بررسی: مهر ۱۴۰۵ (اکتبر ۲۰۲۶) · مبنا: بستهٔ تحویل اولویت ۱۰

## ۱. جمع‌بندی

پروژه پایهٔ معماری خوبی دارد: لایه‌بندی تمیز (Domain / Application / Infrastructure / Web)، کنترل دسترسی چندلایه (Permission + Scope شرکت/شعبه/قلمرو)، Audit، Concurrency خوش‌بینانه، Outbox/DLQ برای ERP و مستندات فارسی مفصل. اما سه ضعف جدی داشت که پیش از هر استقرار واقعی باید رفع می‌شدند:

1. **لایهٔ دادهٔ SQL Server مقیاس‌پذیر نبود.** در هر درخواست، کل ۴۲ جدول بارگذاری می‌شد.
2. **حالت ورود Demo (یک رمز مشترک برای همهٔ کاربران) پیش‌فرض بود** و در Production هم بدون هیچ مانعی اجرا می‌شد.
3. **آزمون مرورگر (Chromium) هیچ‌وقت سبز نشده بود** و چند باگ واقعی رابط کاربری را پنهان می‌کرد؛ از جمله اینکه ثبت سرنخ از فرم همیشه شکست می‌خورد.

علاوه بر این، **مرحلهٔ هشتم نقشهٔ راه (خدمات و SLA) کاملاً پیاده‌نشده بود.**

## ۲. نقاط قوت

- معماری Modular Monolith با جهت وابستگی کنترل‌شده (آزمون معماری خودکار).
- امنیت سمت سرور: نشست سمت سرور، SecurityVersion، OIDC با PKCE، Cookie حداقلی، Anti-forgery، Rate Limit، Security Headers، Data Protection مشترک.
- اعمال Scope روی Query و Mutation و جلوگیری از گسترش ناخواستهٔ دامنه.
- Concurrency خوش‌بینانه با `Version` و پیام فارسی مناسب.
- یکپارچگی ERP با Idempotency، Retry/Backoff، Dead Letter و Correlation ID.
- خروجی CSV امن در برابر Formula Injection.
- Migrationهای قابل بازگشت با اسکریپت Idempotent، قفل و نگهبان تاریخچه.

| 14 | متوسط | Field Masking (مرحلهٔ دوم نقشهٔ راه) پیاده نشده بود. | **رفع شد.** شناسهٔ ملی، تلفن، ایمیل، مانده/سقف اعتبار و حاشیهٔ سود پیشنهاد بر اساس چهار مجوز جدید Mask می‌شوند. ویرایش مشتری بدون مجوز کامل ممنوع است تا مقدار Maskشده روی مقدار واقعی ذخیره نشود. |
| 15 | متوسط | قفل حساب بر اساس نام کاربری وجود نداشت؛ فقط Rate Limit بر اساس IP اعمال می‌شد. | **رفع شد.** ۵ تلاش ناموفق در ۱۵ دقیقه حساب را ۱۵ دقیقه قفل می‌کند (Distributed Cache و Redis). نام کاربری ناموجود هم به همان شکل قفل می‌شود تا وجود حساب فاش نشود. پاسخ 429 هم صفحهٔ توضیح و `Retry-After` دارد. |
| 16 | پایین | آزمون‌ها گزارش پوشش کد نداشتند. | **رفع شد.** CI با `dotnet-coverage` پوشش را جمع می‌کند، گزارش HTML و خلاصه را منتشر می‌کند و اگر پوشش Domain زیر ۷۵٪ یا Application زیر ۸۰٪ برود، شکست می‌خورد (اکنون ۸۲٫۱٪ و ۸۵٫۴٪). Runnerها به xUnit تبدیل نشدند، چون تغییری در رفتار نمی‌داد. |

### اصلاحات جانبی که در همین دور پیدا شد

- مقدارهای Maskشده در صفحهٔ راست‌به‌چپ وارونه نمایش داده می‌شدند (`55*****0218`). با `<bdi dir="ltr">` رفع شد.
- هر استثنای `UnauthorizedAccessException` که در Controller گرفته نمی‌شد، خطای 500 می‌داد. یک فیلتر سراسری آن را به 403 تبدیل می‌کند.
- کلید Cache دسترسی‌ها به v4 تغییر کرد تا Snapshotهای قدیمی پس از استقرار، مجوزهای جدید را فوراً بگیرند.

## ۴. تطبیق با نقشهٔ راه ۱۰ مرحله‌ای

| مرحله | وضعیت | کمبودهای اصلی |
|---|---|---|
| ۰ — تصمیم‌ها | مستند شده | — |
| ۱ — پایهٔ فنی | کامل | آزمون واحد استاندارد |
| ۲ — امنیت و ساختار سازمانی | **کامل** | Field Masking و مدیریت نقش/مجوز اضافه شد |
| ۳ — Customer Master | کامل | Tier (فقط Segment وجود دارد) |
| ۴ — هستهٔ فروش | کامل | — |
| ۵ — قیمت و پیشنهاد | تقریباً کامل | Promotion، Price List مستقل |
| ۶ — سفارش و ERP | تقریباً کامل | Inventory Check، Reconciliation |
| ۷ — شبکهٔ نمایندگان | ناقص | Commission، Guarantee، Training، Evaluation، Ranking، Split Credit |
| ۸ — خدمات و SLA | **قبلاً صفر؛ اکنون پیاده‌سازی شد** | اعلان ایمیل/پیامک، تقویم کاری |
| ۹ — گزارش‌ها | کامل | KPI خدمات |
| ۱۰ — پرتال و موبایل | کامل | تبدیل شکایت پرتال به پرونده خدمات |

## ۵. قابلیت جدید: ماژول خدمات و SLA

جزئیات کامل در [docs/phase-8-service-desk-fa.md](phase-8-service-desk-fa.md). خلاصه:

- ثبت پرونده با دسته، کانال و اولویت؛ صف مرتب بر اساس فوریت SLA.
- تریاژ و تخصیص مسئول؛ SLA جداگانه برای پاسخ اول و حل، با وضعیت «در خطر» و «نقض‌شده».
- قاعدهٔ توقف SLA هنگام انتظار برای مشتری.
- ارجاع خودکار دوسطحی به کارتابل سرپرست یا مدیر با Background Worker.
- الزام علت ریشه‌ای و اقدام اصلاحی برای حل پرونده؛ رضایت مشتری (CSAT)؛ بازگشایی کنترل‌شده.
- ثبت در Timeline مشتری و انتقال در Merge/Unmerge.
- Migration، اسکریپت‌های Idempotent/Rollback، و آزمون‌های دامنه، HTTP و مرورگر.

## ۶. اولویت‌بندی پیشنهادی ادامهٔ کار

1. اجرای Persistence Tests روی SQL Server واقعی در CI. این آزمون‌ها در این بررسی به‌علت نبود SQL Server اجرا نشدند. منطق EF با Provider درون‌حافظه‌ای و ترجمهٔ پرس‌وجوها با `ToQueryString` بررسی شد، اما مسیر تکرار خودکار هنگام برخورد کد فقط با SQL Server واقعی قابل آزمون است.
2. انتقال بقیهٔ فهرست‌ها (فرصت‌ها، پیشنهادها، سفارش‌ها، Audit) به `ICrmQuerySource` و ادامهٔ مسیر Async (ضعف ۱۰).
3. تکمیل مرحلهٔ ۷ (کمیسیون، ارزیابی و رتبه‌بندی نماینده).
4. اتصال شکایت پرتال به پرونده خدمات و افزودن KPIهای خدمات به گزارش‌ها.
5. ایجاد نقش جدید از رابط کاربری. اکنون فقط مجوزهای نقش‌های موجود قابل ویرایش‌اند.
