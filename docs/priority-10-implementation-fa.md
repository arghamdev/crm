# اولویت ۱۰ — پرتال نماینده و CRM موبایل

## دامنه و تحلیل شکاف

مبنای این مرحله، بخش‌های «Portal نماینده» و «Visit و Mobile CRM» سند جامع است. این تحویل، نمونه آزمایشی در همان ASP.NET Core MVC، Razor، HTMX، CSS سازگار با Tailwind و JavaScript است؛ پیش‌نمایش نیز در ورودی یکپارچه قبلی ادغام می‌شود.

| نیاز | وضعیت پیش از این مرحله | تصمیم این نسخه |
|---|---|---|
| پرتال مختص نماینده | فقط DealerUser و پرونده داخلی وجود داشت | فضای `/portal` با Scope دقیق Dealer و شرکت |
| سفارش‌گیری | گردش Quote/Order داخلی موجود بود | ثبت درخواست با قیمت خوانده‌شده از سرور؛ بررسی داخلی و پیوند الزامی به سفارش موجود برای تأیید نهایی |
| قیمت، موجودی، تحویل و اسناد | Adapterهای ERP/مالی نمونه | Port مختص پرتال؛ DTO بدون Cost/Margin، ذکر زمان و منبع، سند نمونه مجاز |
| سرنخ نماینده | ورود محدود نماینده به Lead مجاز نبود | درخواست ثبت؛ ایجاد Lead فقط پس از بررسی داخلی؛ حفاظت نمونه ۳۰ روزه با کنترل تعارض |
| شکایت و Claim | پرتال نداشت | درخواست قابل پیگیری، پاسخ عمومی و گردش Submitted/InReview/Accepted/Rejected/Cancelled |
| کاربران نماینده | اداره از داخل IAM | فهرست کاربران همان نماینده؛ درخواست دعوت/لغو؛ تأیید مسئول IAM، بدون خودارتقایی دسترسی |
| بازدید میدانی | فعالیت فرصت موجود بود؛ مدل Visit نبود | برنامه بازدید مشتری مجاز، Check-in، Complete، Cancel و ثبت نتیجه |
| ثبت موقعیت | سیاست مرورگر بسته بود | اختیاری، فقط با اقدام و رضایت کاربر در صفحه موبایل؛ مختصات معتبر و زمان کنترل‌شده |
| قطع ارتباط | صف موبایل وجود نداشت | صف موقت حافظه همان تب؛ ارسال صریح، رسید idempotency و توقف روی تعارض |
| چند نسخه UI | پیش‌نمایش یکپارچه اخیراً اصلاح شد | حفظ index.html و منوی واحد؛ بدون فایل جزئی به‌عنوان ورودی اصلی |

## مرزهای مدل و امنیت

- DealerId، CompanyId، BranchId و قیمت سفارش از فرم قابل اعتماد نیستند؛ مالک و دامنه از نشست و Grant جاری استخراج می‌شوند.
- پرتال فقط با Grant صریح نوع Dealer فعال می‌شود؛ Company grant به‌تنهایی جای آن را نمی‌گیرد. نماینده تعلیق‌شده/فاقد قرارداد مؤثر امکان ثبت جدید ندارد.
- درخواست سفارش، رزرو موجودی، تأیید اعتبار یا سفارش قطعی ERP نیست. پاسخ پذیرفته‌شدن درخواست نیز باید همین تفاوت را روشن نگه دارد.
- نمایش سفارش فقط از پیوند صریح درخواست متعلق به همان نماینده انجام می‌شود؛ اشتراک مشتری، مجوز مشاهده همه سفارش‌های او نیست.
- DTO کاتالوگ پرتال Cost، Margin، اطلاعات سایر نمایندگان و Credential ندارد.
- دعوت کاربر، حساب PendingActivation با نقش ثابت DealerUser و همان Scope می‌سازد؛ فعال‌سازی هویت بیرونی در IAM انجام می‌شود و پیام واقعی ارسال نمی‌شود.
- بازدید متعلق به کاربر برنامه‌ریز و مشتری مجاز اوست. هیچ Branch یا Owner ارسال‌شده از مرورگر باعث گسترش دسترسی نمی‌شود.
- برای تغییر وضعیت، ExpectedVersion و OperationId لازم است؛ ارسال مجدد همان فرمان رسید قبلی را برمی‌گرداند و تغییر Payload با همان شناسه رد می‌شود.
- Audit شامل شناسه‌ها و عمل است؛ متن شکایت، شرح بازدید و مختصات در Audit عمومی کپی نمی‌شوند.

## قرارداد Offline نمونه

صف فقط در حافظه JavaScript همان تب، حداکثر ۵۰ عمل و حداکثر ۸ ساعت نگه داشته می‌شود. هیچ پاسخ مالی، رمز، Cookie، Token یا تصویر در LocalStorage/IndexedDB/Service Worker ذخیره نمی‌شود. بازخوانی یا بستن تب، صف ارسال‌نشده را از بین می‌برد و قبل از خروج هشدار داده می‌شود. این محدودیت در خود صفحه نوشته می‌شود.

ارسال خودکار در پس‌زمینه نداریم؛ کاربر «ارسال صف» را می‌زند. سرور در هر ارسال دوباره نشست، شرکت، مشتری، مالک، مجوز و Version را بررسی می‌کند. خطای احراز هویت/مجوز یا Conflict ارسال را متوقف می‌کند؛ هیچ last-write-wins خودکاری وجود ندارد. ابتدا پیام نتیجه و سپس تازه‌سازی/تصمیم کاربر لازم است. زمان ثبت سمت دستگاه صرفاً زمان رخداد ادعایی است و از زمان دریافت سرور تفکیک می‌شود.

GPS اختیاری است. نبود مجوز یا خطای دستگاه مانع ثبت بازدید بدون مختصات نیست. مختصات اثبات قطعی حضور محسوب نمی‌شود. نگهداری و پاک‌سازی Production، مدیریت دستگاه و Offline پایدار رمزنگاری‌شده نیازمند سیاست مصوب سازمان‌اند.

## خارج از ادعای این تحویل نمونه

اپ بومی، مسیریابی بهینه نقشه، Push/SMS واقعی، امضای دیجیتال، بارگذاری عکس با اسکن بدافزار، رزرو موجودی ERP، پرداخت واقعی، احراز هویت دعوت‌شده در IdP و Offline پایدار پس از بستن مرورگر، اجراشده محسوب نمی‌شوند. قرارداد و مسیر تصمیم این موارد مشخص است؛ بدون منبع/زیرساخت واقعی ادعای استقرار عملیاتی نمی‌شود.

## پیاده‌سازی و قرارداد مسیرها

| مسیر | روش | مجوز و خروجی |
|---|---|---|
| `/portal` | GET | Portal.Read با Grant دقیق Dealer؛ Razor و دادهٔ همان نماینده |
| `/portal/requests` | POST | Portal.Submit؛ اعتبارسنجی و ثبت درخواست، سپس redirect/HTMX redirect |
| `/portal/requests/{id}/cancel` | POST | ثبت‌کننده، همان Dealer، وضعیت باز و ExpectedVersion |
| `/portal/invoices/{id}/export` | POST | Portal.Read و Dealer.Financial.Read؛ CSRF، no-store، Audit و CSV |
| `/partner-requests` | GET | Portal.Review در دامنهٔ رکورد |
| `/partner-requests/{id}` | GET / POST | فرم بررسی و تصمیم؛ مجوز مستقل Lead.Create/Administration.Manage/Order.Read در صورت نیاز |
| `/mobile` | GET | Mobile.Visit.Read و Customer.Read؛ روز UTC، بازدیدهای خود کاربر |
| `/mobile/visits` | POST | برنامه‌ریزی آنلاین؛ شناسهٔ عملیات و مشتری مجاز |
| `/mobile/visits/{id}` | POST | Mobile.Visit.Write؛ انتقال وضعیت با ExpectedVersion و رسید idempotency |

فرم‌های معمول Razor بدون JavaScript نیز مسیر POST دارند. HTMX برای خطای 422 و تعارض 409 ناحیهٔ خطای همان صفحه را به‌روزرسانی می‌کند. صفحهٔ موبایل برای ارسال صف `Accept: application/json` دارد؛ پاسخ غیر JSON یا HX-Redirect به‌عنوان پایان نشست/پاسخ نامعتبر، ارسال را متوقف می‌کند. timeout دریافت پاسخ ۱۵ ثانیه است و retry با همان OperationId انجام می‌شود.

سه Entity جدید: `PortalRequest`، `MobileVisit` و `MobileOperationReceipt`. کلید یکتای عملیات شامل شرکت، کاربر و OperationId است. Version توکن هم‌زمانی است. برای حفاظت سرنخ، عنوان با یکسان‌سازی فاصله، حروف فارسی/عربی و Unicode به کلید هش تبدیل می‌شود؛ ایندکس یکتای فیلترشده جلوی دو تأیید هم‌زمان را می‌گیرد. این Match سادهٔ نمونه است؛ شماره ثبت/تلفن و داوری تداخل واقعی باید جایگزین معیار عنوان شوند. کلید منقضی هنگام بررسی درخواست بعدی آزاد می‌شود و تاریخچهٔ حفاظت باقی می‌ماند.

سفارش موجود به یک درخواست سفارش پرتال متصل می‌شود؛ ایندکس یکتای فیلترشده از اتصال هم‌زمان تکراری جلوگیری می‌کند. پذیرش درخواست به معنی پذیرش ERP نیست و وضعیت سفارش از همان رکورد داخلی خوانده می‌شود.

پایان بازدید یک رویداد `VisitCompleted` در Customer 360 ایجاد می‌کند؛ replay رویداد دیگری نمی‌سازد. Merge/Unmerge شناسه‌های بازدید و درخواست پرتال را در Manifest نگه می‌دارد و CustomerId آن‌ها را منتقل/بازگردانی می‌کند. شرکت و دامنهٔ تاریخی رکورد تغییر نمی‌کند؛ مجوز مشتری مقصد هم مجدداً بررسی می‌شود. تغییر نسخه، صف قدیمی را به تعارض می‌برد.

Migration: `202609270008_PortalMobileSelfService`، schemaهای `portal` و `mobile`، FK به Dealer/Customer/User، تاریخ‌ها با دقت ۳، مبالغ decimal و مختصات decimal(9,6). Snapshot و DataStore/Seed هم‌زمان به‌روز شده‌اند. `CompatibleMigrationsIdGenerator` شناسه‌های ۱۲رقمی تحویل‌های قبلی را حفظ می‌کند و شناسهٔ جدیدِ scaffold را ۱۴رقمی می‌سازد؛ تاریخچهٔ موجود بازنویسی نمی‌شود.

## قرارداد تکمیل قابلیت‌های وابسته به محیط

| قابلیت | طراحی لازم پیش از فعال‌سازی واقعی |
|---|---|
| عکس بازدید | ذخیره‌ساز خصوصی؛ Upload موقت → قرنطینه → اسکن بدافزار → انتشار لینک مجاز؛ محدودیت حجم/نوع، حذف EXIF و retention |
| Offline پایدار | انتخاب دستگاه مجاز، رمزنگاری با کلید دستگاه، ابطال و پاک‌سازی هنگام لغو حساب، نگهداری محدود و گزارش تعارض؛ دادهٔ مالی در cache عمومی قرار نگیرد |
| مسیر و نقشه | Provider نقشه، سیاست GPS، ترتیب پیشنهادی قابل اصلاح؛ الگوریتم مسیریابی بدون ثبت رضایت اجرا نشود |
| کمپین قیمت | شناسهٔ کمپین، بازهٔ اعتبار و گروه نماینده از ERP؛ تطبیق قیمت و تاریخ اعتبار هنگام سفارش؛ فعلاً قیمت پایه بدون کمپین نمایش داده می‌شود |
| IdP و دعوت واقعی | اتصال حساب PendingActivation به هویت بیرونی تأییدشده، انقضای دعوت، Audit تحویل؛ بدون اعطای نقش انتخابی توسط نماینده |
| ERP و مالی | `IPortalReadSource` با کلید شرکت/نماینده؛ منبع و زمان واقعی، وضعیت ناقص/منقضی، تطبیق با صورت‌حساب رسمی |

پیش‌نمایش HTML اجرای سمت کاربرِ دادهٔ ساختگی است. رکوردهای نمونه ممکن است در LocalStorage ذخیره شوند، اما صف آفلاین در حافظه است. این پیش‌نمایش جایگزین احراز هویت و کنترل دسترسی MVC نیست.
